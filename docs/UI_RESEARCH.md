# UI 与技术设计说明

## 设计目标

这个项目的界面目标不是做成通用后台模板，而是做成一个更适合“景观设计前期工作流”主题的产品型工作台。

设计上强调：

- 信息层级清晰
- 页面之间有连续的工作流感
- 结果展示兼顾结构化与可阅读性
- 既适合录屏展示，也适合继续开发

## 界面策略

### 1. 总览页先讲清价值

`/overview` 不是单纯的欢迎页，而是承担三个作用：

- 快速说明项目定位
- 展示当前工作流进度
- 用图表和指标建立“这个项目是完整产品”的第一印象

### 2. 结果页面强调结构化表达

任务书和场地分析结果不是只把 JSON 原样贴出来，而是通过卡片、分段信息和图表辅助理解，让结果更适合展示和讲解。

### 3. 设置页承担“调试后台”角色

设置页集中放置运行模式、模型参数和提示词模板，这样能把“展示面”和“调试面”分开，也方便后续继续接入新的模型能力。

## 组件设计取向

项目使用了以下几类界面构件：

- 页面头部 Hero：统一每个页面的标题、说明和主操作
- 指标卡片：用于总览页快速传达关键状态
- 图表卡片：用于补足工作流成熟度和 Token 使用情况
- 通用内容卡片：承载任务书、案例、JSON 结果和配置项

这种拆分方式兼顾了复用性与页面节奏控制。

## 为什么选择这些技术

- `Vue 3`：适合以组合式方式组织页面和业务逻辑
- `TypeScript`：让结构化结果、工作流输入输出和静态数据更可控
- `Pinia`：适合管理跨页面联动和持久化前的统一状态
- `Vue Router`：天然适合把流程拆成多页面工作台
- `Element Plus`：提供成熟的表单、上传、表格和反馈组件
- `ECharts`：适合做总览页的图表表达

## 技术与产品的一致性

这个项目的技术选择基本服务于一个方向：让“工作流产品感”比“页面堆砌感”更强。

具体体现在：

- 路由划分围绕流程节点，而不是单纯围绕视觉模块
- 状态组织围绕工作区，而不是围绕单页局部状态
- 服务层围绕业务能力，而不是围绕页面文件

## 后续可继续优化的方向

- 给任务书和场地分析增加更强的导出视图
- 增加结果对比和版本差异展示
- 增加移动端下更细致的阅读和录入体验
- 把图表与历史记录联动做得更深入
- 为多人协作场景预留更明确的信息架构
