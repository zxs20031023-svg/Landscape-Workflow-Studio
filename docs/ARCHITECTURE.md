# 架构说明

## 1. 架构目标

这个重写版的目标不是“把原有 Python UI 再做一遍”，而是构建一套：

- 可独立运行
- 可作品集展示
- 可继续扩展
- 对前端面试官更友好

的完整前端项目。

## 2. 分层方式

### 视图层

位于 `src/views/`

- `overview/`：工作台总览
- `knowledge-base/`：规范知识库管理
- `design-brief/`：设计任务书生成
- `site-analysis/`：场地分析与在线案例检索
- `project-assets/`：历史与结果资产中心
- `settings/`：项目参数与运行模式

### 组件层

位于 `src/components/`

- `layout/`：整体应用外壳
- `panels/`：卡片、JSON 展示、案例卡片等
- `charts/`：ECharts 图表

### 状态层

位于 `src/stores/workflow.ts`

统一管理：

- 项目设置
- Token 统计
- 知识库状态
- 最近一次任务书/场地分析结果
- 推荐项目与已选案例
- 在线案例检索结果
- 历史记录

### 服务层

位于 `src/services/`

- `fileParser.ts`：解析 txt/pdf/docx
- `knowledgeBaseService.ts`：分块、预检、去重、检索
- `rulesEngine.ts`：规则引擎
- `recommendationService.ts`：案例推荐与在线案例导入
- `llmService.ts`：演示模式 / 远程模型调用
- `workflowService.ts`：组织完整工作流
- `storage.ts`：本地持久化

## 3. 数据流

### 设计任务书

1. 用户输入需求
2. 从知识库中检索相关规范片段
3. 调用演示模式或远程模型
4. 使用规则引擎修正结果
5. 把结果写入历史记录与当前工作区

### 场地分析

1. 用户输入场地描述或上传文件
2. 调用演示模式或远程模型
3. 使用场地规则补充建议
4. 基于分析结果做案例推荐
5. 勾选结果同步到任务书链路

## 4. 为什么用 Pinia

这个项目最大的价值在于“状态联动”：

- 在场地分析页勾选案例
- 到任务书页自动带入
- 导入在线案例后同步到推荐列表
- 结果进入历史中心

这些逻辑如果拆散在页面本地状态里，会非常难维护。Pinia 可以把这类工作流状态收在一个中心仓库里。

## 5. 为什么使用浏览器端知识库

因为用户要求是“独立 Vue 3 前端项目”，且不能改动原始仓库。

如果仍依赖 Python 后端，就会出现：

- 新前端不能单独运行
- 需要额外做 API 封装
- 原项目必须联动改造

因此这里采用了“轻量前端知识库”方案：

- 文本分块
- SHA-256 去重
- 关键词/片段检索

它不等价于完整向量数据库，但足够保留产品工作流和交互闭环。
