# 架构说明

## 架构目标

这个项目的目标不是简单复刻某个原型页面，而是把景观设计前期分析流程整理成一个结构清晰、便于演示和扩展的前端应用。

架构上优先保证：

- 前端可以独立运行
- 页面之间状态能联动
- 工作流步骤有清晰的服务层边界
- 后续能平滑接入真实模型服务或中间层接口

## 分层设计

### 视图层

位于 `src/views/`，对应具体页面与交互入口：

- `overview/`：展示项目概况、进度、统计和最近活动
- `knowledge-base/`：负责知识库导入、文件预检和文档管理
- `site-analysis/`：负责场地分析输入、分析结果和案例推荐
- `design-brief/`：负责任务书输入、生成结果和导出
- `project-assets/`：负责历史记录与产出沉淀
- `settings/`：负责运行模式、模型参数和提示词模板配置

### 组件层

位于 `src/components/`，承载通用界面模块：

- `layout/`：应用框架与整体页面布局
- `panels/`：通用卡片、指标面板、结果展示面板
- `charts/`：Token 用量和工作流成熟度相关图表

### 状态层

位于 `src/stores/workflow.ts`，负责统一管理：

- 项目设置
- 提示词模板
- Token 统计
- 知识库状态
- 最近一次场地分析和任务书结果
- 推荐案例、在线案例检索与选择状态
- 历史记录与资产快照

Pinia 在这里承担的是“工作流总线”的角色，而不是单纯的数据缓存。

### 服务层

位于 `src/services/`，按能力拆分：

- `fileParser.ts`：解析上传文件内容
- `knowledgeBaseService.ts`：文档预检、分块、去重和轻量检索
- `recommendationService.ts`：本地案例推荐、在线案例目录检索和导入
- `rulesEngine.ts`：对任务书和场地分析结果做规则校正
- `llmService.ts`：远程模型调用与演示模式回退
- `workflowService.ts`：编排任务书与场地分析工作流
- `storage.ts`：浏览器本地快照持久化

### 数据层

位于 `src/data/`，主要包括：

- 合规规则
- 语义映射
- 本地案例库
- 在线案例目录

这些静态数据为演示模式和前端侧规则能力提供基础支撑。

## 核心数据流

### 知识库导入

1. 用户导入内置规范或上传文件
2. `fileParser.ts` 提取文本
3. `knowledgeBaseService.ts` 完成预检、切片和去重
4. 文档写入 Pinia
5. 状态同步保存到 `localStorage`

### 场地分析

1. 用户输入场地描述
2. `workflowService.ts` 调用 `llmService.ts`
3. 若为远程模式则请求模型，否则使用演示逻辑生成结果
4. `rulesEngine.ts` 对结果补充规则修正
5. `recommendationService.ts` 基于分析结果推荐案例
6. 结果、推荐项和历史记录写入全局状态

### 任务书生成

1. 用户输入设计需求
2. 从知识库中检索相关片段
3. 组合场地分析结果、参考案例和检索命中片段
4. `llmService.ts` 生成结构化任务书
5. `rulesEngine.ts` 补充合规与边界提醒
6. 结果进入历史记录并保存在工作区

## 本地持久化策略

当前项目通过 `localStorage` 保存工作区快照，内容包括：

- 项目设置
- 知识库状态
- 最近一次任务书与场地分析结果
- 推荐案例和选择状态
- 在线案例检索结果
- 历史记录

这样做的好处是：

- 页面刷新后能恢复当前工作进度
- 无需依赖后端会话状态
- 便于作品集和演示场景快速复现

## 为什么不用独立后端知识库

项目目标强调“可独立运行的前端工程”。如果继续依赖原有后端服务，会带来几个问题：

- 新项目无法单独部署或演示
- 需要额外维护接口层和会话状态
- 会增加环境配置复杂度

因此当前采用浏览器端轻量知识库方案，用最小实现保留核心工作流。

## 可扩展方向

- 把模型请求迁移到受控后端代理
- 增加真实在线案例搜索接口
- 引入更完整的导出能力
- 引入多项目工作区或云端持久化
- 将轻量检索替换为嵌入式向量检索方案
